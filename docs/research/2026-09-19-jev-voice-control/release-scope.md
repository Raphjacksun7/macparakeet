# Voice Control implementation and release scope

Audit date: 2026-09-19. Source audit of the active `feat/jev-voice-control` worktree during integration. This matrix compares implemented behavior with the [full feature plan](../../../plans/active/2026-09-19-jev-voice-control.md) and [routing catalog](routing-catalog.md). Later implementation changes must update the affected rows.

**Current verdict:** the branch implements the central voice-to-action architecture and a working dynamic browser goal loop. It does not yet implement every route in the full feature plan, and it is not a qualified stable release. A PR can accurately deliver a substantial explicitly enabled developer beta with a demonstrated goal loop. Describing it as the completed full feature or a ready stable release would overstate the current source and evidence.

## Distribution and agent access

`AppFeatures.voiceControlEnabled` is **false**. `--enable-voice-control` works only in DEBUG builds. Stable builds therefore do not expose this feature through that argument. This is a deliberate gate, not a full public launch.

The browser extension is currently loaded unpacked with an explicit developer installer and separately built `macparakeet-browser-host` executable. [Browser setup](../../../integrations/voice-control-browser/README.md) accurately documents this. Missing stable-distribution work includes signed/notarized host embedding, stable extension identity/publication, supported browser-channel installation/removal, packaged-app onboarding and verification on a fresh user installation. Safari has AX coverage only; no Safari extension target exists. The extension supports the top document and open shadow roots, not cross-origin frames, closed shadow roots, file pickers or rich editors.

There is **no new public `macparakeet-cli` Voice Control command**. Existing library/Transform CLI commands do not expose the new live control runner. The app's typed instruction field and the internal qualification harness are not agent-native CLI parity. The plan explicitly calls CLI a future possible surface, so it is not a prerequisite for the present developer beta; adding it later requires a defined app-IPC/consent boundary, CLI changelog, integration documentation and contract tests. The native-messaging host is a browser transport, not a general automation API.

## What the demonstrations establish

The [browser evidence report](browser-implementation-evidence.md) records a real headless Chrome extension/native-host/socket/live-Jev run against a dynamic synthetic flight form, with independent final DOM assertions. Its recorded input was typed, three fixture-specific confirmations were automatically acknowledged, and a disposable loopback permission compensated for headless `activeTab` gesture limits. It proves the dynamic control loop, not production toolbar consent, human confirmation UX, microphone latency or real-site compatibility. Failed recording-development runs are also recorded.

The [implementation log](implementation-log.md) separately records a native AX/live-Jev two-field synthetic goal. It does not establish Mail/Safari/Finder compatibility. Any later recorded-speech trial should state whether audio came from a physical microphone, a prerecorded file, or synthetic speech; those are different evidence classes.

## Remaining work for a coherent PR and full release

For a coherent PR, keep the feature gated; make the title, description and walkthrough match the implemented rows above; include exact final regression results and runtime artifacts; resolve outstanding safety findings; provide reproducible developer setup and known compatibility limits. Update the plan's proposal-only status to reflect actual implementation without marking unfinished routes complete. The existing HTML walkthrough presents proposed scope and must clearly distinguish it from current availability.

For the user's requested full feature, the unavailable capability rows remain real implementation work: contextual repair/numbered choices, richer precise editing/spelling and inverses, explicit sequences, supported window/tab/system/domain operations, content-reading/cross-app workflows, and richer target feedback. OCR/grid is explicitly optional in the plan and should be separately scoped, not silently claimed.

For stable distribution, finish browser packaging, named native/browser/speech-engine compatibility trials, representative end-to-end latency/correctness evaluation, physical interruption/confirmation/accessibility qualification, regression checks for existing capture modes, and normal signed/notarized release verification. A successful fixture video or passing focused suite does not replace these gates.
